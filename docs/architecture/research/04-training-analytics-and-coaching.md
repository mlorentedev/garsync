# Research: Training analytics and coaching layer for garsync

*Research date: 2026-09-23. Intended repo location: `docs/architecture/research/04-training-analytics-and-coaching.md`.*

**Bottom line.** Everything a serious coaching layer needs is either (a) standard published math that garsync can implement itself from Garmin data it already fetches, or (b) a composite score Garmin already computes but that garsync throws away — and almost none of it needs a machine-learned model. The correct architecture is a deterministic, auditable metric layer (TRIMP/hrTSS → CTL/ATL/TSB, HRV baseline + CV, RHR trend, sleep debt/SRI, monotony/strain, EF/decoupling, race-equivalent predictions) plus a small, explicitly-uncertain recommendation layer that shows its inputs and refuses to speak when the signal is weak. The two genuine data gaps are per-second activity streams (needed for intervals, decoupling, power/pace-duration curves) and any body-composition series (needs the FitDays scale, which is only reachable via a reverse-engineered cloud API). The trap to avoid is the one the literature has already documented twice over: ACWR-style load ratios and ML injury-risk scores produce confident numbers that do not survive external validation, while the honest, well-validated interventions are boring (progressive overload, consistent volume, taper parameters, sleep regularity).

## Method note

Evidence is labelled **MEASURED** (I fetched the source and read the text), **CLAIMED** (vendor/README/blog asserts it), **INFERRED** (my reasoning from measured facts). ## Findings

### 1. Load and fitness models

1. **TRIMP (Banister) is an exponential heart-rate-reserve integral.** Load per sample ≈ `duration × HRr × e^(b·HRr)` where `HRr = (HR − HRrest)/(HRmax − HRrest)`, `b ≈ 1.67 men / 1.92 women` (Banister's original sex-specific constants), summed over the session. **MEASURED** — Runalyze's archived implementation of exactly this is readable in `inc/core/Calculation/Trimp/Calculator.php`: `sum += t/60 * hr * exp(B * hr)` with `hr = (bpm - rest)/(max - rest)`, and it deliberately uses `%HRmax` rather than `%HRreserve` "to be independent of regular changes of the resting heart rate". Note the practical consequence: TRIMP from a *single average HR* systematically underestimates intervals, because the exponential is applied to the mean instead of the distribution — Runalyze feeds it the full HR histogram. [Runalyze TRIMP calculator source](https://raw.githubusercontent.com/Runalyze/Runalyze/support/4.3.x/inc/core/Calculation/Trimp/Calculator.php) (2026-09-23) · [Fellrnr: training impulse](https://fellrnr.com/wiki/TRIMP) (2026-09-23)

2. **TSS is defined so that one hour at threshold = 100.** `TSS = (sec × NP × IF) / (FTP × 3600) × 100`, where `IF = NP / FTP`. **MEASURED** — quoted verbatim by TrainingPeaks' own article (fetched successfully: `trainingpeaks.com/learn/articles/...` works, `help.trainingpeaks.com` returns 403). [TrainingPeaks: Estimating TSS](https://www.trainingpeaks.com/learn/articles/estimating-training-stress-score-tss/) (2026-09-23)

3. **hrTSS is the heart-rate fallback and is explicitly weaker than power/pace TSS.** TrainingPeaks states hrTSS "is based on time in heart rate training zones derived from an athlete's lactate threshold heart rate… the calculation is made using an estimate of the amount of accumulated TSS in an hour, given the level of exertion", and that it "doesn't do as good of a job of incorporating intensity and duration"; it is the default when TSS/rTSS/sTSS cannot be computed. **MEASURED** (same host). For a Garmin-only source this matters: hrTSS (zone-time based, using Garmin's own zone data) is a better load estimator than avg-HR TRIMP, and both are inferior to a full HR-histogram TRIMP. [TrainingPeaks: TSS vs hrTSS](https://www.trainingpeaks.com/learn/articles/training-with-tss-vs-hrtss-whats-the-difference/) (2026-09-23)

4. **CTL/ATL/TSB is a two-parameter exponential smoothing of the load series, not a Banister fit.** `CTL_today = load·λ_f + (1−λ_f)·CTL_yesterday`, `λ = 2/(N+1)`, `N = 42` (fitness) and `7` (fatigue); `TSB = CTL − ATL`. The 42/7 "day" constants are half-lives of **14.7 and 2.4 days**, which surprises most people who read the numbers as an averaging window. **MEASURED** — Fellrnr's derivation and pseudo-code. Intervals.icu documents the algebraically equivalent incremental form (`today = yesterday + (load − yesterday)/timeConstant`, defaults 42 / 7), noting it cannot use the CTL/ATL/TSB names for trademark reasons. [Fellrnr: Modelling Human Performance](https://fellrnr.com/wiki/Modeling_Human_Performance) (2026-09-23) · [Intervals.icu forum: math behind fitness/fatigue](https://forum.intervals.icu/t/question-regarding-math-behind-fitness-fatigue/63699) (2026-09-23)

5. **Runalyze's public documentation is the clearest statement of the *interpretation* problem with PMC.** It publishes ATL and CTL as a *percentage of the athlete's all-time maximum* precisely because absolute values are not comparable between athletes, defines "Easy TRIMP" as the maximal next-day load that keeps TSB at 0, and adds training monotony (variation of daily TRIMP). **MEASURED** — [Runalyze: understanding the calculations](https://blog.runalyze.com/tutorial/runalyze-understanding-the-calculations/) (2026-09-23). This is directly reusable design guidance for garsync: never show raw CTL without a personal reference.

6. **The Banister impulse-response model is a different, richer object than PMC, and PMC has a known structural flaw.** Banister models fitness and fatigue as separate leaky integrators plus weighting constants (`fitness = fitness·e^(−1/r1) + load`, `performance = k1·fitness − k2·fatigue`) and can show a steady state *improving* performance; the TSB simplification cannot — in pure PMC, training only ever lowers performance and only rest reduces fatigue. **MEASURED** — Fellrnr documents both models and names this limitation explicitly. The scientific-validation claim that "Banister's is the most experimentally validated" is **CLAIMED** there. [Fellrnr](https://fellrnr.com/wiki/Modeling_Human_Performance) (2026-09-23)

7. **ACWR: 7-day load / 28-day load — and every threshold attached to it is contested.** Garmin implements the same idea as "Load Ratio" and states the balanced band is **0.8–1.4**, visible only after two weeks of training, with per-athlete optimal ranges (**MEASURED**, Garmin manual). The academic criticisms are severe and specific: (a) Impellizzeri et al. argue the ACWR is used as if it were causal when no causal evidence supports manipulating it, and that its ratio form is mathematically unstable (**MEASURED** abstract, full text paywalled); (b) Lolli et al. show the conventional ACWR calculation is mathematically coupled — the acute term is part of the chronic term — producing spurious correlation (**MEASURED**); (c) the EWMA variant (Williams et al.) was proposed because it is "a more sensitive indicator of injury likelihood than rolling averages", i.e. the *calculation method* changes the answer (**MEASURED** abstract); (d) a 2026 systematic review + multilevel meta-analysis still reports that "practical utility remains debated because of methodological heterogeneity… calculation methods, time-window definitions, sport types, and injury definitions" (**MEASURED** abstract). [Garmin Load Ratio](https://www8.garmin.com/manuals/webhelp/GUID-AC520B63-3C82-4266-90F6-6E9F22D5F76E/EN-US/GUID-200689D7-F65C-40F0-BB82-3C51236C676A.html) (2026-09-23) · [Impellizzeri 2020, IJSPP](https://journals.humankinetics.com/view/journals/ijspp/15/6/article-p907.xml) (2026-09-23) · [Lolli 2019, BJSM](https://bjsm.bmj.com/content/53/15/921) (2026-09-23) · [Williams 2017, BJSM EWMA](https://bjsm.bmj.com/content/51/9/749) (2026-09-23) · [2026 meta-analysis, PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC13520966/) (2026-09-23)

8. **EPOC is the bridge between Garmin's numbers and the load literature.** Garmin's acute load is defined in the manual as "a weighted sum of your excess post-exercise oxygen consumption (EPOC) for the last several days", and the Garmin blog adds that an activity's contribution fades and is gone after 10 days, with chronic load (via load ratio) on a longer window. EPOC itself is a Firstbeat-indirect-estimation method published as a white paper. **MEASURED** (manual + Garmin blog; the *white paper PDF itself was not retrievable in this session* — the download page returned a 512-byte stub, so the EPOC algorithm details are **CLAIMED**). Practical point: `activityTrainingLoad` is exposed per activity by the Garmin Connect API, so garsync can build a load series from Garmin's own EPOC-derived per-session load instead of re-deriving TRIMP. [Garmin fenix 8 manual: Acute Load](https://www8.garmin.com/manuals-apac/webhelp/fenix8series/EN-SG/GUID-E2B2F911-6FB7-45D9-B71B-1D393B0080C9-4283.html) (2026-09-23) · [Garmin blog: training status](https://www.garmin.com/en-GB/blog/garmin-training-status-and-how-to-use-it/) (2026-09-23) · [Firstbeat: EPOC and Training Effect](https://www.firstbeat.com/en/science-and-physiology/epoc-and-training-effect/) (2026-09-23)

### 2. Recovery and readiness

9. **The defensible HRV triad is ln rMSSD (trend), a rolling baseline, and the coefficient of variation of the weekly mean — not a single night's value.** The CV framing comes from Plews et al.'s elite-triathlete case work ("is variation in variability the key to effective training?") and the follow-up monitoring literature; the load-response review cited by Athletica is Plews 2013 (PubMed 23852425). **MEASURED** (titles, journal, year, DOI verified on PubMed/Springer; effect sizes not extracted). [Plews 2012, Eur J Appl Physiol](https://pubmed.ncbi.nlm.nih.gov/22367011/) (2026-09-23)

10. **Garmin's HRV Status is a 7-day mean against a personal range, requiring three weeks of wearing the watch to sleep.** Balanced = 7-day average inside baseline; Unbalanced = above/below; Low = well below; "Poor" / no status = insufficient data. **MEASURED** — Garmin owner's manual. Crucially for garsync, the *numbers* behind that status are in the payload: the library's typed model exposes `weeklyAvg`, `lastNightAvg`, `lastNight5MinHigh`, `status`, and a `baseline` object with `lowUpper`, `balancedLow`, `balancedUpper`, `markerValue`. **MEASURED** — `garminconnect/typed.py` (`HrvSummary`, `HrvBaseline`) in the cloned repo. Garmin does not expose rMSSD per night as a first-class series, but `lastNightAvg` per day is enough to compute ln-rMSSD trend and weekly CV in garsync. [Garmin fenix 9 manual: HRV Status](https://www8.garmin.com/manuals/webhelp/GUID-708A8F4D-9A78-49CF-9528-DE109BBCC472/EN-US/GUID-9282196F-D969-404D-B678-F48A13D8D0CB.html) (2026-09-23) · [python-garminconnect typed models](https://github.com/cyberjunky/python-garminconnect/blob/master/garminconnect/typed.py) (2026-09-23)

11. **DFA α1 should be treated as a research artifact, not a coaching input.** The original method (α1 crossing 0.75 for aerobic threshold, 0.5 for anaerobic) came from Gronwald/Rogers et al. and is published in *Frontiers in Physiology*; **MEASURED** (paper fetched). Marco Altini's 2022 re-evaluation — after processing best-case indoor, artifact-cleaned, Kubios-grade data — concludes "it is undeniable now that we cannot promote the use of a universal threshold (0.75)… even in the best circumstances possible, the data is still not useful at the individual level", citing Rogers/Berk/Gronwald 2022 (*Sports*) and Mateo-March et al. 2022 (EJSS) showing 10–15 bpm individual errors and no individual-level relationship. **MEASURED**. Verdict for garsync: do not ship α1 thresholds. [Rogers et al. 2021, Frontiers](https://www.frontiersin.org/journals/physiology/articles/10.3389/fphys.2020.596567/full) (2026-09-23) · [Altini: updated view on DFA α1](https://www.marcoaltini.com/blog/updated-view-on-hrv-analysis-during-exercise-and-dfa-alpha-1) (2026-09-23)

12. **Orthostatic tests measure something real and different (autonomic response to posture change); Garmin does not provide them.** A 2024 narrative review covers the physiological basis of lying→standing HR/HRV transitions as a monitoring tool, and Polar ships a productised protocol (supine, then standing, compared against a personal baseline). **MEASURED** — abstract + Polar support page. garsync cannot compute this without a controlled protocol with a chest strap or phone; an approximation ("first 2 minutes after standing, using overnight HR vs morning HR") is **INFERRED** and should be labelled as such if shipped. [Orthostatic testing review, PubMed 39259398](https://pubmed.ncbi.nlm.nih.gov/39259398/) (2026-09-23) · [Polar: what and how of the orthostatic test](https://support.polar.com/en/support/the_what_and_how_of_orthostatic_test) (2026-09-23)

13. **Sleep debt and sleep regularity are both computable from what garsync already stores, and both have primary sources.** Sleep debt: Van Dongen et al. 2003 showed that 14 days at 6 h time-in-bed produced neurobehavioural impairment equivalent to 24 h of total sleep deprivation, with cumulative, dose-dependent cost — i.e. debt should be modelled cumulatively against a *personal need*, not against a population norm. **MEASURED** (abstract fetched). Sleep Regularity Index: Phillips et al. 2017, defined as the likelihood that two time-points 24 h apart are the same sleep/wake state, ranging −100 (reversed) → 0 (random) → +100 (perfect), with a reference implementation in the GGIR R package and minimum-data caveats (≥5 valid overlapping days). **MEASURED** — [Van Dongen 2003](https://www.med.upenn.edu/uep/assets/user-content/documents/VanDongen2003CumulativeCost.pdf) (2026-09-23) · [Phillips 2017, Sci Rep](https://www.nature.com/articles/s41598-017-03171-4) (2026-09-23) · [GGIR CalcSleepRegularityIndex](https://rdrr.io/cran/GGIR/man/CalcSleepRegularityIndex.html) (2026-09-23)

14. **Garmin's composites are opaque weighted sums over the same short list of inputs, and only the inputs — not the scores — have independent validation.** Training Readiness is "continuously calculated and updated throughout the day using these factors: sleep score (last night), recovery time, HRV status, acute load, sleep history (last 3 nights), stress history (last 3 days), dive history (last 24 hours)", with bands 95–100 Prime / 75–94 High / 50–74 Moderate / 25–49 Low / 1–24 Poor. **MEASURED** — Garmin manual. Training Status is a VO2max-vs-acute-load interpretation with eight named states (Peaking, Productive, Maintaining, Strained, Unproductive, Overreaching, Recovery, plus no-status), and HRV is a factor where supported. **MEASURED** — Garmin blog. On validation: a 2025 review of composite health scores across vendors catalogued the contributors and found the methodology/transparency lacking; a separate 2025 study validated nocturnal RHR and HRV against ECG across Garmin Fenix 6, Oura Gen 3/4, Polar Grit X Pro and Whoop 4.0 (13 participants). **MEASURED** (abstracts; exact correlations not extracted here). The Garmin HRV payload also exposes per-factor contributions (`sleepScoreFactorPercent`, `recoveryTimeFactorPercent`, `acwrFactorPercent`, `hrvFactorPercent`, `stressHistoryFactorPercent`) — i.e. Garmin's own readiness decomposition is retrievable. **MEASURED** — `typed.py` (`TrainingReadiness`). [Garmin fenix 9 manual: Training Readiness](https://www8.garmin.com/manuals/webhelp/GUID-708A8F4D-9A78-49CF-9528-DE109BBCC472/EN-US/GUID-C21BE0C8-A08E-4DA1-B6C6-2E0E2DDDB372.html) (2026-09-23) · [Doherty et al. 2025, Transl Exerc Biomed](https://doi.org/10.1515/teb-2025-0001) (2026-09-23) · [Nocturnal RHR/HRV validation 2025, Physiol Rep](https://pmc.ncbi.nlm.nih.gov/articles/PMC12367097/) (2026-09-23)

### 3. Performance and progression

15. **VO2max estimation: vendor-specific and not externally validated in anything I could find.** Garmin estimates VO2max from heart rate and performance data and explicitly delegates the estimates to Firstbeat; its race predictions are then derived from that VO2max plus "several weeks of your training data". **MEASURED** — Garmin manual (fenix 8 race predictions, manual wording). A Firstbeat white paper on a "heart rate variability and speed based VO2max estimation method from any freely performed workout" exists and its URL is live, but the PDF body was not retrievable in this session — **CLAIMED**. [Garmin fenix 8 manual: predicted race times](https://www8.garmin.com/manuals/webhelp/GUID-EECCAC99-90D6-4AB1-9A3A-EC433D3365E2/EN-US/GUID-31B2458A-859A-4A34-AB83-224E4A29387A.html) (2026-09-23) · [Firstbeat VO2max white paper (PDF)](https://firstbeat.com/wp-content/uploads/2017/06/white_paper_VO2max_30.6.2017.pdf) (2026-09-23, body not retrieved)

16. **A self-computed open alternative exists: "Effective VO2max".** Runalyze estimates it per activity from the heart-rate-to-pace relation (optionally with elevation), averages it as current form, and applies an *individual correction factor derived from the athlete's best race and its heart rate* — an honest acknowledgment that HR response varies per person. It also adds a "marathon shape" modifier (weekly kilometres 2/3, long-run length 1/3, six-month window by default) so that race prognoses are not purely VO2max-based. **MEASURED** — Runalyze docs. [Runalyze: understanding the calculations](https://blog.runalyze.com/tutorial/runalyze-understanding-the-calculations/) (2026-09-23)

17. **Race-time equivalence: the Riegel power law and its critics.** `T₂ = T₁ × (D₂/D₁)^1.06` is the widely used form (Riegel, 1977/1981; the exponent's provenance is properly attributed to Kennelly 1906 as a power-law model, per a 2022 modelling preprint comparing power laws with critical power). **CLAIMED** for the exponent from secondary calculators; **MEASURED** for the power-law-vs-CP framing. Practical stance: ship Riegel equivalence as a *display-formatting* tool with visible uncertainty, never as a race plan. [Modelling human endurance: power laws vs critical power (preprint)](https://doi.org/10.1101/2022.08.31.506028) (2026-09-23) · [Empirical study of race times in recreational runners](https://doi.org/10.1186/s13102-016-0052-y) (2026-09-23)

18. **Critical power / W′: worth implementing only if garsync gets power or treadmill-pace streams.** `P = W′/t + CP` (Monod & Scherrer 1965, as summarised by GoldenCheetah), valid roughly 2 min–1 h; above CP, W′ depletes and reconstitutes below it. The W′bal integrating model with a reconstitution time constant τ is the standard operationalisation, and its own methodological literature (2021 IJSPP review; 2021 bi-exponential reconstitution paper; 2025 reconstitution-modelling paper) shows the τ model is still being revised. **MEASURED** — [GoldenCheetah: CP and W′](https://www.goldencheetah.org/) (2026-09-23) · [W′ Balance Model: mathematical and methodological considerations](https://doi.org/10.1123/ijspp.2021-0205) (2026-09-23) · [Bi-exponential W′ reconstitution](https://link.springer.com/article/10.1007/s00421-021-04874-3) (2026-09-23)

19. **Efficiency Factor and decoupling are trivial to compute and unusually well suited to a solo hobbyist.** Decoupling (Pw:HR / Pa:HR) compares first-half vs second-half efficiency of a steady aerobic session; typical values are 0–10% and a drift above ~5% in an aerobic ride is treated as a signal of insufficient aerobic base. **MEASURED** — TrainingPeaks' own explainer (fetched) and Runalyze's glossary (fetched; Runalyze attributes the concept to Joe Friel). These require per-second HR + pace/power, which garsync does not yet store. [TrainingPeaks: Efficiency Factor and Decoupling](https://www.trainingpeaks.com/blog/efficiency-factor-and-decoupling/) (2026-09-23) · [Runalyze glossary: aerobic decoupling](https://runalyze.com/glossary/aerobic-decoupling) (2026-09-23)

20. **Interval detection is a solvable, non-ML problem.** The `cycleRtools` R package implements `interval_detect()` by supplying the expected number of sections to a changepoint analysis of power data — i.e. retrospective detection of efforts "not in any way marked in the device data (e.g. as 'laps')" (**MEASURED**, package docs). Vendor strategies: Athletica markets automatic detection "independent of workout plans or manual lap marks" plus automatic compliance evaluation (**CLAIMED**). For garsync, the pragmatic route is Garmin's own lap/auto-lap structure first, changepoint detection as a later enhancement. [cycleRtools interval_detect](https://rdrr.io/cran/cycleRtools/man/interval_detect.html) (2026-09-23) · [Athletica Interval IQ](https://athletica.ai/blog/interval-iq-automatic-interval-detection) (2026-09-23)

21. **Periodisation/taper has the strongest evidence base of anything in the "intervention" category.** Bosquet et al. 2007 meta-analysis (MSSE) and Mujika & Padilla's "Scientific Bases for Precompetition Tapering Strategies" both formalise the taper as a progressive non-linear load reduction with volume down sharply, frequency slightly, and *intensity maintained*; a 2023 PLOS ONE meta-analysis of endurance athletes reports a significant time-trial improvement pre→post taper (SMD = −0.45). **MEASURED** (abstracts). [Bosquet 2007, MSSE](https://journals.lww.com/acsm-msse/fulltext/2007/08000/effects_of_tapering_on_performance__a.19.aspx) (2026-09-23) · [Mujika & Padilla, MSSE](https://doi.org/10.1249/01.mss.0000074448.73931.11) (2026-09-23) · [PLOS ONE 2023 taper meta-analysis](https://doi.org/10.1371/journal.pone.0282838) (2026-09-23)

### 4. How commercial adaptive systems actually work

22. **TrainerRoad Adaptive Training: not a physiological model, a difficulty-rating system.** Workouts carry a "Workout Level" per zone; the athlete carries a "Progression Level" 1–10 per zone; the gap between them yields six difficulty labels (Recovery, Achievable, Productive, Stretch, Breakthrough, Not Recommended). Completing a workout nudges the relevant Progression Level up or down; FTP changes rescale all levels while preserving relative strengths; missed time causes levels to decay. **MEASURED** — TrainerRoad's own blog (fetched; the support-centre article returns 403). This is the single most copyable idea in the entire survey: an explicit, auditable *difficulty ladder per zone* with a personal position on it. [TrainerRoad: introducing Adaptive Training](https://www.trainerroad.com/blog/introducing-adaptive-training-the-right-workout-every-time/) (2026-09-23)

23. **Athletica: Banister with guardrails, and it publishes the architecture.** Its methodology page states the load layer is "standard Banister-derived math, the same family of calculations TrainingPeaks and most of the industry use", modified three ways: it updates continuously from history rather than from test days; load and response are integrated (HRV chief among the response signals, citing Plews 2013) so response modulates how aggressively the next block builds; and prescriptions run inside guardrails (form floor that is shallower for beginners, a per-day spike ceiling scaled to current fitness, taper into a race). It explicitly separates the layers: "the load prescription is deterministic… not a black box and not a trained model"; ML sits upstream in profile/threshold detection. It cites its own model description as SPSR241 (Zignoli & Laursen, 2024). **CLAIMED** (vendor methodology page, fetched; the SPSR241 PDF was linked but not fetched). [Athletica: Banister training load](https://athletica.ai/methodology-banister-training-load) (2026-09-23) · [Athletica methodology hub](https://athletica.ai/methodology) (2026-09-23)

24. **Runna: adaptation is event-driven and coarse, not physiological.** Its documented behaviours: "Plan Realignment" fires when the app detects more than three missed workouts or a week of training and offers plan-length-dependent options; "Pace Insights" compares achieved paces against plan targets in intervals/tempo/time-trial/long runs and adjusts future paces when you consistently beat or miss them; an illness/injury adjustment runs 3–14 days then a gradual return phase. Nothing about HRV, HR drift or readiness. **CLAIMED** — Runna support articles (search-verified, host not fetched). [Runna: plan realignment](https://support.runna.com/en/articles/10026375-how-to-use-the-plan-realignment-feature) (2026-09-23) · [Runna: Pace Insights](https://support.runna.com/en/articles/14656203-what-are-pace-insights-and-how-do-they-work) (2026-09-23) · [Runna: adapting for illness](https://support.runna.com/en/articles/12809806-feeling-unwell-how-to-adapt-your-training-plan) (2026-09-23)

25. **Whoop and Oura: inputs are documented, weights are not.** Whoop's developer docs state Recovery uses previous-day measurements and sleep — RHR, HRV, respiratory rate, sleep duration/quality, skin temperature, SpO2 — and that the Recovery object carries "the objective measurements that factored into the score"; Strain is a 0–21 non-linear score "based on the Borg Scale of Perceived Exertion", normalised so 21 is the maximal daily cardiovascular load, and a WHOOP patent (US 2014/0309542) describes weighting heart-rate-reserve data for cardiovascular intensity. **MEASURED** — Whoop developer docs and the patent listing. Oura's daily-readiness object exposes nine contributor fields — `activity_balance`, `body_temperature`, `hrv_balance`, `previous_day_activity`, `previous_night`, `recovery_index`, `resting_heart_rate`, `sleep_balance`, `sleep_regularity` — plus `score`, `temperature_deviation`, `temperature_trend_deviation`; I read this from a mirror of Oura's OpenAPI spec and a generated SDK because the official docs page is JS-rendered and the help-centre page 403s. **MEASURED** (spec fields) / **INFERRED** (that this is byte-identical to Oura's current spec). [Whoop developer: Recovery](https://developer.whoop.com/docs/developing/user-data/recovery/) (2026-09-23) · [WHOOP 101](https://developer.whoop.com/docs/whoop-101/) (2026-09-23) · [Oura OpenAPI mirror (readiness contributors)](https://raw.githubusercontent.com/api-evangelist/oura-ring/refs/heads/main/openapi/oura-ring-daily-readiness-routes-api-openapi.yml) (2026-09-23) · [oura-toolkit API reference](https://ouratoolkit.com/api/operations/single_daily_readiness_document_v2_usercollection_daily_readiness__document_id__get/) (2026-09-23)

26. **The open-source landscape is thinner than it looks, and one "obvious" project is dead on GitHub.** GoldenCheetah: **GPL-2.0, 2,205 stars, last push 2026-09-23** (active), and it implements CP/W′ modelling, W′bal/dFRC, TSS, Banister and PMC, "Ae/An TISS", power peaks and time-in-zone — the best readable reference implementation of the load models (**MEASURED**, GitHub API + project site). Runalyze: the GitHub mirror is **archived, last push 2019-11-08, 226 stars, no licence field**, though the product (runalyze.com) is alive and its hosted documentation/glossary pages are current — treat the archived repo as documentation of the formulas, not as a dependency (**MEASURED**, GitHub API). Intervals.icu: closed source, but its forum documents the exact CTL/ATL/TSB recurrence and it offers automatic eFTP estimation from single maximal efforts (**MEASURED** for the formula post and the features page). WKO5: closed, with a Power-Duration Model v2, mFTP/FRC/TTE/Stamina and dFRC; the scientific-basis page 403'd, so those claims are **CLAIMED** from vendor pages surfaced in search. For HRV computation inside garsync: NeuroKit2 (**MIT, 2,366 stars, pushed 2026-09-06**) and pyhrv (**BSD-3-Clause, 341 stars, pushed 2026-06-17**) both provide rMSSD and non-linear HRV measures (**MEASURED**, GitHub API). ### 5. The output side: interventions, and how not to be confidently wrong

27. **The weekly report a real coach issues is small and concrete.** Across the sources surveyed, the deliverable set is: (a) volume and intensity distribution for the coming week, expressed as time-in-zone targets; (b) a load target (CTL trajectory) with an explicit ceiling on how fast it may rise; (c) a recovery verdict that can *remove* a session rather than only describe it; (d) taper timing anchored to an event. Garmin's own vocabulary (load ratio 0.8–1.4 balanced; the eight Training Status states; "Strained" → "take it easy") and Athletica's guardrails (form floor, spike ceiling, taper window) are two independent renderings of the same list. **MEASURED/CLAIMED** as noted in findings 7, 14, 23.

28. **HRV-guided training has modest, mixed evidence — so it can justify *reordering*, not revolution.** Three meta-analyses surfaced: HRV-guided vs predefined training for physiological/aerobic markers (**MEASURED** abstract, "eight articles qualified"); a 2021 systematic review with meta-analysis (JSAMS) of wearable-monitored HRV-guided endurance training (**MEASURED** abstract); and a VO2max-focused meta-analysis in endurance athletes (**MEASURED** abstract). None of them support the strong claim that HRV guidance reliably beats good planning; the honest reading is a small average benefit in some populations, with high individual variability. [Appl Sci 2020 meta-analysis](https://www.mdpi.com/2076-3417/10/23/8532) (2026-09-23) · [JSAMS 2021 meta-analysis](https://doi.org/10.1016/j.jsams.2021.04.012) (2026-09-23) · [IJERPH 2020 VO2max meta-analysis](https://www.mdpi.com/1660-4601/17/21/7999) (2026-09-23) · [PMC8507742](https://pmc.ncbi.nlm.nih.gov/articles/PMC8507742/) (2026-09-23)

29. **Injury-risk prediction from wearable data is where confident wrongness lives.** A systematic review of 30 studies (204 models) found that "no studies externally validated a prediction model" and that only 27% used both regression and ML approaches (**MEASURED** abstract). The broader clinical-ML literature reaches the same conclusion (Christodoulou et al. 2019, cited within that review: no performance benefit of ML over logistic regression). Combined with the ACWR critique in finding 7, the design consequence is sharp: garsync must not emit numeric injury probabilities. Show *load and recovery state*, name the uncertainty, and make the recommendation falsifiable and cheap to ignore. [Just how confident can we be in predicting sports injuries? Sports Med 2022](https://pubmed.ncbi.nlm.nih.gov/35689749/) (2026-09-23)

30. **A defensible automated recommendation engine for noisy consumer data looks like a rules engine with a confidence gate, not a model.** Ingredients that the sources actually support: prefer deterministic, auditable formulas (Athletica's own framing); require concurrence of ≥2 independent signals before recommending a change (e.g. HRV below baseline **and** RHR up **and** sleep debt high); express outputs as ranges/bands with the *inputs shown*; refuse to act when the input is stale or missing (Garmin's own "no status" pattern); and keep a decision log so recommendations can be scored later. The "single night's HRV is noise" and "no universal threshold" warnings (findings 9, 11) are the reason for the concurrence rule, and the readiness-score transparency critique (finding 14) is the reason for showing inputs. **INFERRED**, but every component cites a measured source above.

## What this means for garsync

**Severity-tagged gaps in the current code (read from the repo at `/home/manu/Projects/garsync`, 2026-09-23):**

1. **BLOCKER — no per-second streams.** `src/garsync/client.py` calls only `get_activities`, `get_heart_rates`, `get_body_battery`, `get_all_day_stress`, `get_hrv_data`, `get_sleep_data`, and stores activity *summaries* (`src/garsync/db/schema.py`: duration, distance, avg/max HR, calories). Without streams, decoupling, EF, MMP/pace curves, interval detection, W′-balance and in-activity α1 are all off the table. The library already ships the parser for detail samples (`garminconnect.get_activity_details()` → `activityDetailMetrics` + `metricDescriptors`, wrapped by `parse_activity_detail_metrics` in `garminconnect/activity_details.py`) — **MEASURED**. Adding a `activity_streams` table is the single highest-leverage schema change.
2. **MAJOR — Garmin's own derived metrics are discarded.** `activityTrainingLoad`, aerobic/anaerobic Training Effect, `normPower`, and the readiness decomposition exist in payloads the library models explicitly (`typed.py`: `Activity.activity_training_load`, `aerobic_training_effect`, `training_readiness` factors) — **MEASURED**. garsync stores `raw_data` JSON but surfaces nothing derived. `activityTrainingLoad` alone gives a Garmin-consistent EPOC-based load series on day one.
3. **MAJOR — HRV is stored as a status *string*.** `biometrics.hrv_balance` holds `hrvSummary.baselineStatus`; the numbers (`weeklyAvg`, `lastNightAvg`, baseline bounds) are present in the same response but never extracted — **MEASURED** (`client.py` vs `typed.py`). Without the nightly number there is no ln-rMSSD trend, no weekly CV, no personal baseline, i.e. no readiness layer at all.
4. **MAJOR — no body-composition series exists in the schema at all.** No weight, body-fat, or lean-mass table; the Garmin client wraps Garmin's body-composition endpoints (library README: "Body Composition & Weight: 7 methods") — **MEASURED**. Body composition is only meaningful if the FitDays scale data lands here; until then, "body composition" stays a chart-less feature.
5. **MINOR — sleep is stored but under-analysed.** `sleep` has start/end timestamps, stages and score, which is exactly the input for sleep debt (vs a personal need) and SRI — **MEASURED** (schema). No derived table exists.
6. **MINOR — no planned-vs-actual and no subjective input.** Every adaptive system surveyed behaves differently when it can compare prescription to execution (TrainerRoad compliance, Athletica compliance evaluation via detected intervals, Runna Pace Insights). garsync has no notion of a plan, and no RPE/notes store, so it can only describe, never coach — **INFERRED**.

**Opinionated build order.** (i) A `derived_metrics_daily` table computed by a pure-Python, unit-tested module: load (hrTSS from zone time or Garmin `activityTrainingLoad`), CTL/ATL/TSB (λ = 2/(N+1), 42/7), ramp rate as 7-day load delta as % of CTL, monotony and strain (mean/SD of daily load), RHR 7-day mean and deviation, HRV ln-trend + weekly CV + baseline z, sleep debt, SRI, plus a "data quality" flag per day. All of it deterministic, all of it reproducible, all of it testable against hand-computed fixtures. (ii) Readiness as a **transparent** z-score sum over three to five named inputs, with the inputs shown in the UI — not a 0–100 black box (a 0–100 could be displayed for familiarity, but the decomposition must be visible). (iii) Streams, then EF/decoupling and interval detection. (iv) Only then a recommendation layer, gated on concurrence and expressed as ranges. Deliberately *not* on the roadmap: ACWR as a decision input (report the Garmin-style load ratio descriptively at most), DFA α1 thresholds, injury probabilities, and any trained model — 30/30 externally-unvalidated is the relevant base rate.

**Product stance.** The differentiator against Garmin Connect is not "more charts"; it is *auditability and continuity*: every number traceable to a formula and a source row, personal baselines instead of population ones, and history that survives vendor UI changes. That is also the honest framing for a portfolio piece — the interesting engineering is the deterministic metric layer with its uncertainty discipline, not a model.

## Open questions and decisions needed

1. **Streams: fetch and store them, or compute on demand?** Storing per-second samples for a multi-year history is a size decision (SQLite + WAL). Recommendation to decide explicitly: start with a 90-day rolling window of stream samples, derived metrics persisted indefinitely.
2. **Whose load number is the canonical one?** Options: (a) Garmin's `activityTrainingLoad` (consistent with the watch UI, not independently documented), (b) self-computed hrTSS from zone time (auditable, comparable across activities), (c) full-histogram TRIMP (best internal-load estimate, needs streams), (d) a per-sport hybrid. I recommend (b) now, (c) after streams, with Garmin's number shown alongside as a cross-check and divergence logged.
3. **Readiness: mirror Garmin or replace it?** A garsync readiness score built from measured inputs is more honest but will disagree with the watch, which is a support burden for a sole operator. Decision needed.
4. **What is the scale's integration path, and does it need a daily cron?** The FitDays cloud API is undocumented; unofficial clients exist (`AboveColin/fitdays` — MIT, 2 stars, pushed 2026-09-14; `AboveColin/HA-Fitdays`; `roquerodrigo/fitdays-api`) — **MEASURED** via GitHub API for the first. Using one means depending on a reverse-engineered, low-star, single-maintainer surface; that is a supply-chain decision, not a coding one, and it should be made knowing the failure mode is a household with no data.
5. **Sleep debt needs a personal "sleep need".** Sources treat need as individual. Options: fixed 8 h, personal median of the last 90 nights, or Garmin's own sleep-need value if exposed. This choice changes the sign of the reported debt and must be stated in the UI.
6. **Do we ever recommend "don't train"?** A system that only describes is safe and useless. Define the rules where garsync is allowed to remove or downgrade a session, and how many concurring signals are required — this is a product decision with a safety edge, not an algorithm decision.
7. **Recommendation audit.** If recommendations are issued, they must be logged with inputs and scored later; otherwise the "confidence" claim is unfalsifiable. Decide now whether that table ships with v1 of the coaching layer.
