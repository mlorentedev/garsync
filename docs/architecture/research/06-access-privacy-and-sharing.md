# Access, Privacy and Sharing for a Personal Health App (garsync v2 research)

**Bottom line.** For v1, keep garsync single-owner and put *two independent* authorization boundaries in front of the data: an application-level session (server-set `__Host-` cookie, passkey-first with TOTP as fallback) that the app owns, and — where the deployment target allows it — Authelia forward auth on the public hostname. Do not build public sharing in v1; the one scenario that actually recurs in a year is "show a doctor/coach something", and an encrypted export covers it at a fraction of the risk of an unauthenticated endpoint onto Article 9 data. Multi-user is a different product with a different legal position and a rewritten data-access layer, justified only when a *second person's own data* needs to live in the system.

Evidence markers: **MEASURED** = I fetched the source and read it in this session. **CLAIMED** = a README/vendor page asserts it. **INFERRED** = my reasoning from measured facts. All access dates 2026-09-23.

## 1. Authentication options for a single-owner app

1. **Authelia is the strongest self-hosted option and is actively maintained** — Apache-2.0, 29,066 stars, last push 2026-09-23, not archived, 132 open issues. It supports passkeys/WebAuthn, TOTP, per-rule access policies, and both forward auth and OIDC. **MEASURED** ([repo metadata](https://api.github.com/repos/authelia/authelia), [WebAuthn config](https://www.authelia.com/configuration/second-factor/webauthn/)).

2. **Passkey-as-second-factor in Authelia is explicitly experimental** — `experimental_enable_passkey_uv_two_factors` is documented as "not considered supported … completely experimental and will be replaced by custom policies"; passkey *login* (`enable_passkey_login`) "only counts as a single factor". **MEASURED** ([WebAuthn](https://www.authelia.com/configuration/second-factor/webauthn/)). Consequence for garsync: on Authelia, a passkey is a convenience factor, not a two-factor credential — the second factor is still TOTP or a security key.

3. **Forward auth is a browser-session mechanism, not an API credential.** Authelia's Traefik integration is `/api/authz/forward-auth` plus `authResponseHeaders: Remote-User,Remote-Groups,Remote-Email,Remote-Name`, and the Traefik-side config must set `trustForwardHeader` and (for upstream trust) `forwardedHeaders.trustedIPs`. **MEASURED** ([Traefik integration](https://www.authelia.com/integration/proxies/traefik/), [Kubernetes ingress](https://www.authelia.com/integration/kubernetes/traefik-ingress/)). A curl script, a mobile app or an LLM agent cannot complete a redirect flow — it gets a 302 to the IdP portal.

4. **Authelia's access-control rules already express the two things garsync needs: location-aware factors and a public exemption.** Policies are `deny` (recommended default), `bypass` (skips authentication entirely), `one_factor`, `two_factor`; criteria include `networks` (matched against the first `X-Forwarded-For` address), `resources` (path regex), `subject` (user/group), and `oauth2:client:<id>` for `client_credentials` tokens. **MEASURED** ([Access Control](https://www.authelia.com/configuration/security/access-control/)). A LAN/tailnet `one_factor` rule plus an external `two_factor` rule is config, not code; a public share path is a `bypass` rule — with the caveat below.

5. **`bypass` cannot be combined with a `subject` restriction** ("the minimum authentication level required to obtain information about the subject is one_factor"), and Authelia's own 2026 advisory shows access-control rules missing due to domain canonicalization (CVE-2026-48794, Low 1.3 weighted, fixed in 4.39.20). **MEASURED** ([Access Control](https://www.authelia.com/configuration/security/access-control/), [GHSA-j748-h363-wqj8](https://github.com/authelia/authelia/security/advisories/GHSA-j748-h363-wqj8)). Translation: expressing a share-link exemption in the IdP is possible but puts the exemption in the layer whose bugs are exactly of this kind. Prefer keeping public exemptions inside the app, where a test can assert them.

6. **Session lifetimes are configurable but the mobile ergonomics depend on `remember_me`.** Defaults: `inactivity: 5m`, `expiration: 1h`, `remember_me: 1M`; `-1` disables remembering, and the docs note the Passkey Login Flow "currently requires remembering sessions if enabled". **MEASURED** ([Session](https://www.authelia.com/configuration/session/introduction/)). Also: stateful in-memory sessions are the default; **Redis is "recommended especially for containerized deployments"** — without it, restarting the Authelia pod logs every device out. **MEASURED** (same page).

7. **Cloudflare Access is a real alternative with a different cost structure.** It issues a global session token (15 min – 1 month, default 24 h) and per-app/policy tokens (immediate – 1 month); when the app token expires it silently re-issues from the global token, and only a global expiry forces an IdP login. It supports per-application and per-user revocation, MFA sessions, and a `401` mode for AJAX sub-requests via `X-Requested-With: XMLHttpRequest`. **MEASURED** ([Session management](https://developers.cloudflare.com/cloudflare-one/identity/users/session-management/)). Note the doc's own warning: app session durations "only control the front door" — the app must still hold its own session.

8. **Cloudflare Access service tokens are the machine/API path**: client-id + client-secret header pair (or a single header via `read_service_tokens_from_header`), explicit duration, rotation with a 1 hour – 30 day grace period, and optional auto-disable of tokens inactive 30–365 days. **MEASURED** ([Service tokens](https://developers.cloudflare.com/cloudflare-one/identity/service-tokens/)). This is the cleanest way to give an agent or a cron client access *if* the app sits behind Cloudflare — and it is a long-lived bearer secret, so it belongs in the agent's secret store, not in code. I could **not verify** the free-tier user limits or the current number of users included in the Zero Trust free plan from primary docs in this session (**GAP**).

9. **Tailnet-only is the only option that removes the attack surface rather than gating it.** Headscale is the self-hosted control server (BSD-3, 44,070 stars, last push 2026-09-23) and the client is open source (BSD-3, 36,802 stars, last push 2026-09-23). **MEASURED** ([headscale](https://api.github.com/repos/juanfont/headscale), [tailscale](https://api.github.com/repos/tailscale/tailscale)). A service reachable only from the tailnet has no public hostname, no ACME surface, and no third party terminating TLS — and on a phone it works because the Tailscale client is a VPN, not a browser plugin. **INFERRED**.

10. **Tailscale Funnel is the escape hatch you should not use for health data.** It publishes a tailnet service to the public internet on ports 443/8443/10000 at `<tailnet>.ts.net`, with non-configurable bandwidth limits and — the important part — "if the most recent command to configure the port was `funnel`, then the port will be completely public". **MEASURED** ([Funnel](https://tailscale.com/kb/1223/funnel)). There is no per-path authorization in Funnel; whatever auth the app has *is* the auth.

11. **Application-level auth means you own the hard parts, and OWASP has the numbers.** Session IDs need ≥64 bits of entropy from a CSPRNG; use `__Host-` prefixed, `Secure`, `HttpOnly`, `SameSite=Strict|Lax` cookies; regenerate the session ID on privilege change; enforce idle and absolute timeouts server-side; never store tokens in `localStorage`/`sessionStorage`; log session lifecycle events. **MEASURED** ([OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)). Passwords: Argon2id with m≥19 MiB, t=2, p=1 as the minimum; bcrypt only for legacy. **MEASURED** ([Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)).

12. **Python libraries that exist and are alive for this job:** `Authlib` (BSD-3, 5,425 stars, last push 2026-08-31) for OIDC *client* flows if garsync consumes Authelia as an IdP; `py_webauthn` (BSD-3, 1,061 stars, last push 2026-06-29 — ~3 months, not dead but slower cadence) for passkey registration/assertion; `fastapi-users` (MIT, 6,243 stars, last push 2026-08-17) for the generic user/password plumbing you probably do not need for one account. **MEASURED** ([authlib](https://api.github.com/repos/lepture/authlib), [py_webauthn](https://api.github.com/repos/duo-labs/py_webauthn), [fastapi-users](https://api.github.com/repos/fastapi-users/fastapi-users)). For a single account, a TOTP secret + Argon2id hash + `py_webauthn` is less machinery than a user framework.

13. **What breaks when the identity provider is down — comparison.** Cloudflare's edge is not going down, but a locked Cloudflare account, a broken Terraform-managed DNS record, or a federated IdP outage all remove access; the app-level session (option A) has no external dependency at all, because the app *is* the IdP; a tailnet-only deployment survives a Headscale outage for already-established WireGuard peers but cannot enroll new nodes (**INFERRED**, not verified); and Authelia being unreachable makes every forward-auth'd route unreachable, including the app's own login page, because Traefik answers before the app does (**INFERRED** — I could not retrieve Traefik's forwardAuth failure semantics; the page did not extract. **Verify on kubelab staging by scaling Authelia to zero.**).

14. **Break-glass paths, ranked by how likely they are to work under stress.** (a) `kubectl port-forward` from a laptop on the tailnet to the pod — bypasses Traefik, Authelia, CrowdSec and TLS in one step, needs only a kubeconfig kept *off* the cluster; (b) a second IngressRoute with no forward-auth middleware restricted by an `IPAllowList` to the tailnet CIDR, committed in Git so it survives reconciliation; (c) hand-editing the middleware under pressure. **(c) is a trap in this repo's shape**: with Argo CD self-sync, a manual emergency patch gets reverted, so the break-glass must be a committed config or an explicit "pause sync" step written in a runbook. **INFERRED**.

## 2. Mobile clients behind forward auth and OIDC

15. **Server-set, first-party cookies are the pattern WebKit itself recommends**, and the reason matters here: ITP deletes script-writable storage (IndexedDB, LocalStorage, Service Worker registrations and caches) after seven days without user interaction, while an OAuth 2.0 flow that consumes a token and establishes "a first-party login session with a server-set Secure and HttpOnly cookie" is the documented Option 1. **MEASURED** ([WebKit ITP](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)).

16. **A PWA added to the iOS home screen has its own storage counter** — "Web applications added to the home screen are not part of Safari and thus have their own counter of days of use", and Apple does not expect first-party data to be deleted. **MEASURED** (same page). So a garsync PWA installed on the home screen will keep its local caches and cookies; a plain Safari tab left untouched for a week will not.

17. **The real mobile failure mode with forward auth is the silent 401, not the redirect.** Authelia users report session-expiry leaving "a non-working only visual aspect of your service" until a hard refresh, and Cloudflare documents the analogous problem for AJAX ("Pages that rely heavily on AJAX or single-page applications can block sub-requests due to an expired Access token without prompting the user to re-authenticate", fix: `X-Requested-With: XMLHttpRequest` → 401). **MEASURED** ([Authelia #6758](https://github.com/authelia/authelia/discussions/6758), [Cloudflare session management](https://developers.cloudflare.com/cloudflare-one/identity/users/session-management/)). Any garsync client must treat 401 as "re-authenticate me", never as "no data".

18. **OIDC refresh behaviour on a phone is specified and non-trivial.** Authelia issues opaque access tokens by default, revokes the previous access *and* refresh token on each refresh, and requires explicit consent when a refresh token is granted (`offline_access`/`offline`). **MEASURED** ([Authelia OIDC FAQ](https://www.authelia.com/integration/openid-connect/frequently-asked-questions/)). MCP's authorization spec adds the modern client rules: OAuth 2.1, PKCE mandatory, resource indicators (RFC 8707) so a token is bound to one audience, refresh rotation for public clients, and a hard prohibition on token passthrough. **MEASURED** ([MCP authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)). A phone client that re-authenticates silently forever requires you to get rotation right; a session cookie requires you to get nothing right.

19. **GAP: passkeys inside an iOS home-screen web app.** I could not verify (primary sources) whether WebAuthn/passkey prompts work reliably in standalone PWAs vs Safari on iOS; the search results returned only SEO content (**MEDIUM confidence**). Treat "passkey login from the installed PWA" as a test to run on the real device before it becomes the only login path.

## 3. Sharing scenarios that will appear

20. **The reference implementation of a safe public link is Immich's**: "The public shared link is generated with a random URL, which acts as a secret to avoid the link being guessed", with optional expiration, password protection, and restricted actions. **MEASURED** ([Immich sharing](https://immich.app/docs/features/sharing/)). Licence flag: Immich is **AGPL-3.0** (114,909 stars, last push 2026-09-23) — cite it as a pattern, do not copy code into MIT-licensed garsync. **MEASURED** ([repo metadata](https://api.github.com/repos/immich-app/immich)).

21. **Grafana's externally shared dashboards add two lessons**: the ability to publish is gated by an RBAC permission (`dashboards.public:write`), and the docs warn that external sharing "could result in a large number of queries to the data sources". **MEASURED** ([Grafana docs](https://grafana.com/docs/grafana/latest/dashboards/dashboard-public/)). A public health dashboard is not just a confidentiality problem; it is an unauthenticated surrogate for your database's query budget.

22. **The moment a link takes an object identifier, you are in OWASP API1 territory.** "APIs tend to expose endpoints that handle object identifiers… Object level authorization checks should be considered in every function that accesses a data source using an ID from the user." **MEASURED** ([OWASP API Security Top 10 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/)). Design share access as *scope-defined projections* (`/share/<token>` returns a fixed document), never as `/api/activities/{id}` with a token in a header.

23. **For an agent/LLM client, the pragma differs from the standard.** If you want an existing MCP client to connect, garsync must be an OAuth 2.1 resource server with protected-resource metadata and audience validation — real work. If you only need *your* agent on *your* machine, a scoped, revocable, hashed-at-rest bearer token stored in the agent's secret store achieves 90% of the value for 5% of the effort. **INFERRED**, with the standard's requirements **MEASURED** ([MCP authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)).

24. **The doctor case is an export case, not a link case.** A clinician has no account on your host, will not enroll a tailnet device, and cannot act on an ephemeral URL in a 15-minute appointment; a PDF/CSV you hand over has no standing attack surface, no revocation problem, and no audit obligation. Where an interoperable shape is useful, the natural target is FHIR `Observation` (vital signs, body composition), which is the shape any future clinician-facing tool will expect. **MEASURED** for the spec ([FHIR R4 Observation](https://hl7.org/fhir/R4/observation.html)); the workflow claim is **INFERRED**.

25. **A coach is the case that justifies a real link**, because it recurs: view-only, expiring, optionally password-protected, revocable, `noindex`, logged. Manage it with one table (`token_hash`, `scope`, `expires_at`, `revoked_at`, `last_accessed_at`) so the same primitive serves the coach link and the agent token. Do not implement two mechanisms. **INFERRED**.

## 4. Data protection: GDPR, at rest, backups

26. **While it is only you, the GDPR likely does not apply at all.** Article 2(2)(c): the Regulation "does not apply to the processing of personal data … by a natural person in the course of a purely personal or household activity", and Recital 18 adds the boundary: "and thus with no connection to a professional or commercial activity". **MEASURED** ([GDPR, EUR-Lex](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32016R0679)).

27. **Publishing to "an indefinite number of people" is where that exemption stopped being read broadly, even before the GDPR.** In *Lindqvist* (C-101/01) the Court held the private/family-life exception "clearly" does not cover "publication on the internet so that those data are made accessible to an indefinite number of people", and it treated "an individual has injured her foot" as health data. **MEASURED** ([judgment summary, EUR-Lex](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:62001CJ0101)). Applied honestly: a publicly viewable garsync dashboard is a different legal category from a private one. **INFERRED**. I found no authority specifically about a data subject publishing *their own* health data, where there is no other data subject whose rights can be infringed — so the practical risk is reputation/inference, not fines (**GAP**, stated as an inference).

28. **Recital 18 closes the "but I'm just the tooling" door if garsync ever hosts others' data**: the GDPR "applies to controllers or processors which provide the means for processing personal data for such personal or household activities". **MEASURED** (same EUR-Lex text).

29. **Health data is Article 9 special-category data** — processing is prohibited absent an exception, with 9(2)(a) explicit consent as the usual basis for a consumer product. **MEASURED** (same text). And Article 32(1)(a) names "the pseudonymisation and encryption of personal data" as the first appropriate technical measure. **MEASURED**.

30. **The obligations that appear the moment garsync serves another person:** Article 30 records of processing activities; Article 33 notification of a personal data breach "not later than 72 hours"; Article 35(3)(b) DPIA where there is "processing on a large scale of special categories of data". **MEASURED** (same text). For a hobby-scale multi-user app "large scale" is arguable, but the DPIA trigger is the least of the costs — the operational ones are below.

31. **Kubernetes gives no at-rest encryption by default, in either place you might assume.** "By default, the API server stores plain-text representations of resources into etcd, with no at-rest encryption"; and for mounted filesystems you must "use a storage integration that provides encrypted volumes *or* encrypt the data within your own application". Even with `--encryption-provider-config` and a local key, that "protects against an etcd compromise, but it fails to protect against a host compromise". **MEASURED** ([Kubernetes: Encrypting Confidential Data at Rest](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/)). So a garsync PVC holding SQLite is unencrypted unless you encrypt it, and a SOPS-encrypted secret is plaintext the moment it becomes a mounted Secret.

32. **SQLCipher is the credible file-level option and it is alive** — BSD-3, 7,280 stars, last push 2026-09-15. Design: AES-256-CBC per page, per-page random IV, HMAC-SHA512 per page, PBKDF2-HMAC-SHA512 with 256,000 iterations by default, WAL and rollback journals encrypted, and "when encrypted, the entire database file appears to contain random data". **MEASURED** ([SQLCipher design](https://www.zetetic.net/sqlcipher/design/), [repo metadata](https://api.github.com/repos/sqlcipher/sqlcipher)). **Unverified:** the maintained Python bindings (`sqlcipher3`, `pysqlcipher3`) — I did not check them, and this is a real adoption cost because SQLCipher is a SQLite fork using internal APIs, so you lose stdlib `sqlite3` (**GAP**).

33. **Where at-rest encryption actually pays in this architecture.** The disk-thief threat is mostly hypothetical on a Hetzner VPS; the *snapshot and backup exfil* threat is not — a MinIO copy, an rclone sync, or a VM snapshot in someone else's bucket is the same data without any of your perimeter. **INFERRED**. Practical order: (1) whatever leaves the host, encrypt first (age/SOPS, or a LUKS-backed volume from kubelab's storage layer); (2) confirm whether the node's disk itself is encrypted by the provider at rest — I could not verify Hetzner's position here (**GAP**); (3) SQLCipher only if you accept losing the stdlib driver, because the running app holds the key anyway.

34. **SQLite gives you a good backup primitive for free, with a privacy bonus.** `VACUUM INTO '<file>'` is documented as "an alternative to the backup API for generating backup copies of a live database", producing a consistent snapshot that "is minimal in size" and where "all deleted content is purged from the backup, leaving behind no forensic traces". **MEASURED** ([SQLite VACUUM](https://sqlite.org/lang_vacuum.html)). For health data, that second property matters: deleted rows do not resurrect in a restore. Back up by `VACUUM INTO`, then age-encrypt the artifact, then move it.

35. **SOPS is a file-encryption tool, and its protection ends at deploy time.** SOPS (MPL-2.0, 23,199 stars, last push 2026-09-21) is the kubelab standard; the age private key is therefore the real boundary and it should live in an offline copy plus a password manager, not only on the cluster. **MEASURED** for repo metadata ([getsops/sops](https://api.github.com/repos/getsops/sops)); the "ends at deploy time" conclusion follows from finding 31 (**INFERRED**).

## 5. Threat model for a public hostname in front of personal health data

36. **The reverse proxy itself is the most concrete, recent, and measured risk in this stack.** Five Traefik advisories were published on 2026-09-07 (CVE-2026-88004 … 88010), including one **critical** (HTTP/3 backend NTLM/Negotiate connection reuse) and — the one that should change your architecture — GHSA-f52w-8j3h-j724: a rootless HTTP/1 request-target "routes as `/` but is forwarded verbatim, bypassing path-scoped routing, middleware guards and access logging", whose PoC shows "a direct unauthenticated request to `/admin` returns `401`, while the same endpoint accessed over the h2c tunnel returns `200`", CVSS 8.8, patched in v3.7.13 / v2.11.57. **MEASURED** ([Traefik advisories](https://api.github.com/repos/traefik/traefik/security-advisories)). Read carefully: **the class of bug that hits forward auth is middleware bypass.** A single boundary at the edge is a single point of failure *and* a single point of bug.

37. **Authelia's own advisory history is the reassuring half**: CVE-2026-48794 (access-control domain canonicalization, Low, fixed 4.39.20), CVE-2026-47203 (username canonicalization in Basic Auth, Medium 6.3 / weighted Low 2.9, LDAP-only), CVE-2026-33525 (XSS in 4.39.15, Low), CVE-2025-24806 (login regulation doubled across username/email logins, Low). **MEASURED** ([Authelia advisories](https://api.github.com/repos/authelia/authelia/security-advisories)). Few high-severity code bugs; mostly misconfiguration-adjacent, which means **your config is the likelier source of an auth hole than their code**.

38. **Traefik defaults to not trusting any proxy** — "by default doesn't trust any other proxies requiring explicit configuration of which proxies are trusted and removes potentially fabricated headers", with `forwardedHeaders.insecure=false` in the official examples. **MEASURED** ([Authelia Traefik integration](https://www.authelia.com/integration/proxies/traefik/)). This is good news for header spoofing, and a footgun for Authelia's `networks` criteria, which match on `X-Forwarded-For` — get the trusted-IP config wrong and your "LAN = one_factor" rule can be spoofed or simply never match.

39. **The application layer is currently the weakest link and it is yours to fix.** garsync today is a FastAPI app with no user identity (per the session plan, it still carries a shared-secret/dev-key path). FastAPI has no built-in auth, so every endpoint's authorization is whatever the code says — and once share links exist, OWASP API1/API3/API5 (object-, property-, and function-level authorization) all become live. **INFERRED**, consistent with **MEASURED** [OWASP API Top 10](https://owasp.org/API-Security/editions/2023/en/0x11-t10/).

40. **What "mature self-hosted projects" actually do about exposure**: they gate the *capability* behind a permission (Grafana's `dashboards.public:write`), they make public artifacts capability-URLs with independent expiry and password (Immich), they offer per-app and per-user revocation with an explicit inactivity cleanup (Cloudflare service tokens), and they default the policy to `deny` (Authelia's recommended `default_policy: 'deny'`). **MEASURED** (sources above).

41. **Realistic attack surface ranking for garsync on a public hostname**, given the above: (1) credential stuffing / password spraying against your one account, mitigated by a strong passkey/TOTP and rate limiting rather than by obscurity; (2) a middleware-routing bug at the edge (finding 36) — the reason app-level auth must also exist; (3) an authorization bug in a share endpoint, which exists only if you build share endpoints; (4) proxy/version CVEs, mitigated by patch cadence, which the Traefik timeline shows is measured in days, not months; (5) the database being copied through a backup path (finding 33). **INFERRED**.

## 6. Private vs public/multi-user: what each forces

42. **Private v1 (single user) forces almost nothing architecturally**: one account, one session, no tenant key, no audit beyond auth events, no onboarding, no DSR tooling, no DPIA. The whole cost is the auth implementation in finding 11 plus a deployment decision. **INFERRED**.

43. **Multi-user forces a tenant boundary into the data-access layer, and SQLite has no row-level security** — enforcement lives in application code, i.e. one forgotten `WHERE user_id = ?` is a cross-tenant leak of health data. Postgres RLS is the alternative, with its own caveats: RLS only applies "if a user has access privileges to a table", "the table's owner is typically not subject to row security policies", "superusers and roles with the `BYPASSRLS` attribute always bypass", and referential-integrity checks "always bypass row security", so a backup can silently omit rows. **MEASURED** ([Postgres row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)). Either way, the repository layer and every query site get rewritten, and every endpoint needs a policy test.

44. **Multi-user forces an identity product, not an identity function**: registration, email verification, password reset/recovery, MFA enrollment and recovery, account lockout, and an account-takeover incident path that ends in someone else's medical data being exposed. Authelia can carry part of this for a small closed group; it is not a consumer signup product. **INFERRED**.

45. **Multi-user turns you into a GDPR controller for other people's Article 9 data** (findings 26–30) and adds audit logging obligations in practice, not only law: an append-only event table (actor, subject, object, action, timestamp, source IP) plus retention, because OWASP's own guidance is to "increase your logging capabilities by including information regarding the full life cycle of sessions". **MEASURED** ([OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)).

46. **A publicly viewable single-owner dashboard is a middle option with its own honest cost.** It keeps the schema and the legal position (you are still the only data subject), but it makes your recovery, body composition and sleep permanently scrapable and correlatable, and — per Grafana's warning — turns your database into an unauthenticated query endpoint. Publish derived aggregates on a separate deployment and database, never the raw streams. **INFERRED**.

47. **The deployment target may remove the choice.** A nan.builders Basic Space deploy is a Dockerfile + env vars on a public hostname with no platform auth (**CLAIMED** — this is the session brief's account of the platform; I did not independently verify NaN's networking or auth features). If v1 ships there, app-level auth is mandatory and forward auth is optional; if v1 ships in kubelab K3s, tailnet-only + Authelia becomes possible and is strictly safer. **INFERRED**.

## What this means for garsync

**v1 (private, single owner) — recommended:**

1. **Decide the deployment first, because it decides the auth.** If garsync lives in kubelab K3s (Hetzner), put it on a private hostname behind Authelia `two_factor` for external requests and `one_factor` for tailnet/LAN, and *also* keep app-level auth. If it ships to NaN Basic Space, app-level auth is the only boundary — build it accordingly and assume the hostname is public. Do not start the auth work before this is settled.
2. **Application-level session, owned by garsync**: passkey-first (py_webauthn) with TOTP recovery, Argon2id for any password, ≥64-bit CSPRNG session tokens in a `__Host-` `Secure` `HttpOnly` `SameSite=Lax` cookie, server-side idle + absolute timeouts, session-ID regeneration on login, and 401-not-redirect semantics for every XHR so the PWA can prompt instead of silently breaking (finding 17).
3. **Do not make forward auth the only gate.** The Traefik 2026 advisories are a middleware-bypass class (finding 36); Authelia's `bypass` policy and `networks` criteria are config-sensitive (findings 5, 38). Two independent boundaries is the design, not belt-and-braces superstition.
4. **Write the break-glass runbook before you need it**: committed second IngressRoute without the forward-auth middleware restricted to the tailnet CIDR, plus `kubectl port-forward` as the emergency path; both must survive Argo CD reconciliation (finding 14).
5. **Sharing in v1 = export, not links.** Emit an age-encrypted PDF/CSV (or a FHIR-shaped JSON for future clinicians) on demand. No unauthenticated route exists in v1, so no share-endpoint authorization bugs exist in v1.
6. **One agent token, scoped and hashed.** A single read-only bearer token for your LLM/agent tooling, stored in the agent's secret store, hashed at rest, revocable, and logged. Skip MCP's OAuth 2.1 resource-server machinery until a third-party client actually needs to connect (finding 23).
7. **Encrypt what leaves the host.** `VACUUM INTO` → age-encrypt → move; verify a restore quarterly. Treat SQLCipher as a later decision tied to the Python-binding cost, not a v1 item (findings 32–34).
8. **Log auth and share lifecycle events into the database** (login success/failure, session creation/destruction, token issue/revoke, share access) — cheap now, and it is exactly the table the multi-user option would otherwise force you to retrofit (finding 45).

**Conditions that would justify moving to public or multi-user later:**

- **Multi-user only when a second person's own data must live in it** (a training partner or coach with their own account) — not merely "wants to see mine". That triggers: tenant key + policy tests on every endpoint, Postgres with `FORCE ROW LEVEL SECURITY` and a non-owner app role (finding 43), an audit log, recovery/MFA flows, DSR export/erasure, and a DPIA-shaped document. Expect the data-access layer to be rewritten, not extended.
- **Public dashboard only when you deliberately want it indexed** (portfolio), and then publish *derived aggregates only* — training volume, streaks, activity counts — from a separate deployment and database, with no weight, body composition, sleep, HRV or resting-HR series. Say out loud that it is permanent and correlatable.
- **A public share endpoint only when sharing becomes recurring** (a coach, weekly). Then build the one share primitive from finding 25, with expiry, revocation, `noindex`, rate limiting, scope-defined projections rather than object IDs, and an explicit test that an unauthenticated request to any other path returns 401.
- **Cloudflare Access only if you need to serve devices that cannot join the tailnet** — and accept that your access control then depends on an account, a Terraform state, and an IdP you do not run (finding 13).
