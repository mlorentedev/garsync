# ADR-009: Storage Substrate, Schema Evolution and the Unit Contract

## Status

Accepted — 2026-09-24. Requires no owner input to proceed; the kubelab migration-ownership question below remains a cross-repo integration point, not a blocker for the schema work.

## Date

2026-09-24

## Context

`src/garsync/db/schema.py` defines `_SCHEMA_V1` behind a `schema_version` table, but there is **no migration mechanism at all**: `init_db` either sees the current version and returns, or runs the whole v1 script. There is no path from v1 to v2.

That is survivable while the schema holds four tables the application owns end to end. It stops being survivable now: this design adds per-second activity streams, a numeric HRV series, weight and algorithm-tagged body composition, nutrition entries, a derived-metric table, a targets table with history, an ingest ledger, a recommendation log and an auth audit table. Every one of those is a schema change, and some of them are schema changes that must be applied to a database that already contains years of history.

Two facts from the research shape the answer. First, the closest project to this one — Endurain — uses **SQLAlchemy + Alembic**, and the maturity of its migrations is part of why it survived long enough to need a feature freeze for *other* reasons. Second, SQLite and PostgreSQL share the `INSERT ... ON CONFLICT ... DO UPDATE` family, so an idempotency contract written once holds on both engines; that is what makes "SQLite for dev, Postgres for prod" cheap **only if decided now**.

A storage-engine survey (brief 03) found no justification for a dedicated time-series database at this scale.

## Options Considered

1. **Hand-rolled numbered SQL migration runner.** Cheap, no dependency, and it works — but it is bespoke infrastructure that must be tested for out-of-order application, partial application, and idempotency, and it has no tooling for inspecting a schema that has drifted.
2. **SQLAlchemy 2.0 + Alembic.** Chosen. Adds a dependency (Discipline Gate: this is a decision, not a snippet) and buys autogenerated diffs, a reviewable migration artifact per change, downgrade paths, and the option of an ORM-free "Core" style that keeps the current repository layer.
3. **Atlas**, the platform's own choice for the *shared* Postgres service. Rejected for the app's own schema: the platform's mandate governs the platform's schema, and a second tool in the same repository for the same concept is exactly the duplication this repository's own standards forbid. Ownership of this boundary must be confirmed with kubelab.
4. **A dedicated time-series engine (Timescale/QuestDB/DuckDB/Influx).** Rejected: operational weight with no measured need at one athlete's data volume; DuckDB remains a candidate for *analytical* side queries, not as the system of record.
5. **Postgres from day one, including local development.** Rejected: it removes the zero-setup dev path and the fixture-based tests that currently make the suite fast, for a workload that is not concurrency-bound.

## Decision

1. **PostgreSQL is the production system of record; SQLite (WAL) remains the development and test engine.** The repository layer keeps a single dialect-agnostic code path built on the shared UPSERT syntax; anything engine-specific is quarantined behind a named module and a test.
2. **Alembic migrations are adopted, and the v1→v2 baseline is generated from the existing schema** with a test that upgrades a v1 fixture database and asserts the result.
3. **Canonical units at rest** (kg, metres, seconds, bpm, ms, °C, kcal), display units only at the edge, conversion the receiver's job. The contract lives in a document plus a test.
4. **A `metric_registry` table** holds metric identity: `code`, `system` (`garsync`, `garmin`, or a real `loinc` code where a defensible one exists), canonical `unit` (UCUM), `dtype`, aggregation rule and polarity. FHIR-flavoured identity **without** a FHIR server.
5. **Raw inputs are retained for anything derived** — impedance, weight, intake, streams — and derived values are recomputed, never hand-edited, so a changed coefficient can be replayed across history.
6. **Body-composition values are stored per algorithm** (`(measurement_id, algorithm)`), never merged into a single field.
7. **`activity_streams` retention is a configured window** (initial 90 days); derived metrics are kept indefinitely.
8. **No subject or tenant column exists on any table (SC-12).** The system holds exactly one person's data, and the insurance-column idea was considered and withdrawn: a column whose value is always `1` is dead weight no test can prove correct, and it invites the cross-tenant leak a second deployment cannot have. If another person ever needs this app, they get a **second instance** — same repository, separate deployment, separate database, their own identity.
9. **The MVP's schema additions are `goals` and nothing else speculative.** `goals` (goal weight, rate band, effective-from) is load-bearing rather than cosmetic: it is the axis the `Body` trend is drawn against (SC-03/SC-06). Nutrition tables are **not** created (SC-01): a later Alembic migration is routine, while a table nothing writes invites a half-built feature.

## Consequences

### Positive

- The schema can grow safely from here on, which is the single cheapest structural change available before four new data domains land.
- One migration history serves dev, test and prod; a reviewer can read a migration as an artifact rather than diffing DDL by eye.

### Negative

- Two new dependencies (SQLAlchemy + Alembic) and a test-suite burden around migrations.
- Two engines means two failure modes; the dialect-agnostic claim needs a test that runs the repository layer against both, not a comment asserting it.

### Neutral

- SQLite remains viable for a small, low-traffic deployment (for example the public demo instance), which preserves the option in ADR-011 without the schema diverging.

## Amendment — 2026-09-25, the shape this decision took (SUB-001)

The choice above lists **autogenerated diffs** among the reasons to adopt Alembic. Implementing it
narrowed that benefit deliberately, and the narrowing belongs in the record rather than in a
recollection:

- **Revisions are written by hand with SQLAlchemy Core ops** (`op.create_table`, `op.add_column`),
  never raw `ALTER` strings, and the repository layer stays on `sqlite3`. This is the ORM-free `Core`
  style the decision explicitly permitted; it keeps one description of the schema instead of three
  (models, revision, DDL) and it is what the first revision required anyway, since a baseline that
  must reproduce an existing database and a revision that carries data movement cannot be
  autogenerated.
- **`alembic autogenerate` is therefore forgone permanently**, not just for the first revision: with
  no declarative models there is nothing to diff against, and the benefit should not be read as still
  available by anyone planning a later table. The substitute is a **drift assertion** — the schema a
  fresh database builds is compared against the schema a migrated v1 database produces
  (`TestAlembicSeam::test_fresh_and_migrated_databases_are_identical`) — plus
  `test_the_baseline_reproduces_the_v1_schema`, which is what makes `alembic stamp` a statement of
  fact rather than of hope.

Any future decision to reintroduce autogenerate is a new decision about the repository layer, and it
should be taken as one.
